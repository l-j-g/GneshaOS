# GneshaOS agent guide

This repository is the NixOS and Home Manager configuration for the GneshaOS
system. Keep changes declarative, reviewable, and safe to build from an
isolated Git worktree.

## Repository map

- `flake.nix` is the entry point. It builds the host named by
  `params.nix.systemSettings.hostName` on `x86_64-linux` and imports the fixed
  machine module at `hosts/cf-fv1/`.
- `params.nix` is the tracked source of truth for user and machine preferences.
  Keep it tracked; Git flakes do not include ignored or untracked files.
- `params.example.nix` is the documented template and evaluation fallback.
- `hosts/cf-fv1/default.nix` contains machine-level services and hardware
  integration. `hosts/cf-fv1/hardware-configuration.nix` is generated by
  `nixos-generate-config`; do not hand-edit it unless explicitly asked.
- `modules/` contains reusable NixOS modules.
- `home/` contains the Home Manager user environment, including Sway, shell,
  editors, fonts, theme, daemons, and desktop scripts.
- `flake.lock` is intentionally pinned. Update inputs only when that is part of
  the request.

## Working rules

- Inspect `git status --short` before editing and preserve unrelated existing
  changes. Do not reset, clean, stash, or overwrite user work.
- Prefer the smallest change that follows the existing module and parameter
  structure. Put user-facing values in `params.nix`, not scattered through
  modules.
- Follow existing Nix style and keep module options, comments, and parameter
  documentation in sync when behavior changes.
- Prefer verified, existing NixOS/Home Manager modules and packaged tools for
  desktop behavior before adding custom implementation code. Keep Nix modules
  declarative and compact; do not embed long shell programs or polling daemons
  in configuration files when an existing package or service provides the
  behavior. If custom code is genuinely required, keep it as a focused,
  separately testable script under `home/desktop/scripts/` and document why a
  packaged alternative was not suitable.
- Never put passwords, tokens, private keys, or machine secrets in the repo.
- Do not run `sudo`, `nixos-rebuild switch`, `nixos-rebuild boot`,
  `nixos-install`, disk/partitioning commands, TPM/LUKS changes, or destructive
  store commands unless the user explicitly requests that operational action.
  Default to evaluation, checks, and dry-run builds.
- Do not change generated hardware configuration, `flake.lock`, or ignored
  machine-local tooling unless the task specifically requires it.
- After a requested change is complete and its relevant build/check succeeds,
  commit the complete scoped change with a concise, descriptive commit message.
  Stage only files belonging to that change; leave unrelated dirty work alone.
- Do not create or move Git tags unless the user explicitly requests tagging.

## Validation

Run the narrowest useful checks, then report exactly what was run and any
environment-dependent limitation.

```sh
# Evaluate the complete flake and its checks.
nix flake check --show-trace

# Parse a changed Nix file when a full check is unnecessary.
nix-instantiate --parse path/to/changed-file.nix

# Build without activating or installing the system.
nixos-rebuild build --flake .#cf-fv1
```

Use the current `hostName` from `params.nix` instead of `cf-fv1` if that value
has changed. Do not use `switch` as a substitute for validation.

## Subagents and worktrees

For every non-trivial task, autonomously delegate independent read-heavy work
without waiting for the user to ask for subagents. Use parallel agents for
codebase mapping, option/API research, review, and validation. Stay single-agent
for a genuinely small, tightly coupled edit where delegation would add more
overhead than value. Keep write-heavy work serialized: two agents must not edit
overlapping files in the same checkout.

For a normal implementation task, use this default sequence:

1. Start `nix_explorer` to map the affected NixOS/Home Manager paths.
2. Start `nix_reviewer` for independent safety and regression checks when the
   change spans multiple files or affects system behavior.
3. After the read-only results are available, start `nix_worker` to implement
   the scoped change in the task worktree.

The parent agent should return the consolidated result; do not make the user
repeat this delegation plan in each task prompt.

- Use `nix_explorer` for read-only repository mapping and dependency tracing.
- Use `nix_reviewer` for read-only correctness, safety, and regression review.
- Use `nix_worker` for implementation only after the change is understood.
- The normal CLI entry point is `codex-nix`, which starts Codex in
  `~/.config/nix`. Do not assume that this checkout is isolated.
- When a task is multi-file, system-affecting, or likely to need parallel write
  work, create/use a dedicated Git worktree under
  `~/src/trees/nix/<task-name>`. For a small, tightly scoped change, working in
  the current checkout is acceptable when it is consistent with the user's
  request and existing dirty state.
- A worktree agent may edit and validate its branch, but must not push, merge,
  activate the host, or discard unrelated work unless explicitly instructed.
- Worktree agents should use `nix flake check`, `nix eval`, and build-only
  commands. They must not use `/etc/nixos` or mutate the running machine as a
  substitute for the worktree.
- Every subagent handoff should include a concise summary, changed files,
  validation commands and results, and any remaining risk.

The project `.codex/config.toml` enables these roles and limits parallelism;
the project `.codex/agents/` files define their focused behavior. Worktrees
are selected by the Codex client, so the instructions above are deliberately
explicit about the isolation requirement.

## Completion standard

A change is ready when the requested behavior is implemented, the relevant
Nix evaluation/build checks pass (or their failure is explained), no unrelated
dirty files were altered, and the final summary names the exact files changed.
